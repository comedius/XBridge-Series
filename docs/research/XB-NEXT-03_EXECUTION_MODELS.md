## 2. Owner-approved direction and limits

- `documented (project-authored)` S0: the owner approved a hybrid direction: compatible Xbox x64 code should ultimately execute natively on host CPUs, while Xbox OS/services/runtime behavior is supplied by an XBridge compatibility layer. The existing interpreter remains reference, diagnostic and fallback.
- `documented (project-authored)` S0: this direction does **not** prove arbitrary Xbox binaries executable and does not authorize JIT, binary rewriting, code patching or real-game execution.
- `unknown`: whether any real commercial Xbox Series X binary can execute under this direction. No real game, proprietary binary, key, firmware or protected asset was obtained, opened or executed.
- `hypothesis`: a future scoped proof could use a synthetic PE32+/AMD64 test case with a controlled compatibility layer; this is a candidate experiment, not an approved implementation.

## 4. Interpretation of the comparison

1. `documented (authoritative, general only)`: CPUID/XGETBV/AVX2/BMI/FMA, Windows x64 ABI, TLS, SEH, virtual memory and Win32 synchronization are public general facts. They do **not** establish Xbox Series X guest behavior.
2. `documented (project-authored)`: S0 approves the hybrid direction and S11 records the current interpreter's narrow scope. Neither is proof that arbitrary Xbox binaries can run.
3. `hypothesis`: ABI matching, TLS translation, host SEH bridging, memory mapping and thread mapping are design candidates. None is implemented or approved by this research package.
4. `unknown`: guest CPUID leaves, AVX2/BMI/FMA requirements, guest ABI, interrupt semantics, syscall surface, memory map, threading rules and privileged-instruction behavior remain open.

## 5. Open decisions and questions

- No owner decision is requested by this package. The final-feasibility question remains open: can a lawful synthetic corpus establish a stable subset of guest behavior without proprietary material?
- Which instruction sets, if any, must a future synthetic proof exercise: baseline AMD64 only, or also AVX2/BMI/FMA? `unknown` without guest evidence.
- Which ABI, TLS, exception and memory assumptions should a compatibility layer expose? `unknown`; public Windows x64 documents provide only candidate general facts.
- How should privileged instructions or guest interrupts be handled without JIT, binary rewriting or code patching? `unknown`.
- What isolation boundary should native guest code use? See `docs/research/XB-NEXT-03_NATIVE_EXECUTION_FEASIBILITY.md` for public-source limitations; no worker-process design is implemented.
